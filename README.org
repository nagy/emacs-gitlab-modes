#+title: gitlab-modes - GitLab merge request and pipeline modes for Emacs
#+author: Daniel Nagy
#+language: en

Read-only Emacs modes for GitLab merge requests and CI pipelines.
One buffer shows one merge request or one pipeline.  A separate mode
shows a collection as a sortable table.  Every display buffer refreshes
itself through =auto-revert-mode= and never blocks Emacs.

The package reads GitLab through the =glab= command line program.  The
Nix build bakes the store path of =glab= into =gitlab-program=, so an
installed package works without =glab= on =PATH=.

* Requirements

- Emacs 30.1 or later
- =glab=, authenticated for the GitLab instance
- Optional: evil, for =gitlab-evil.el=
- Optional: Org, for =ol-gitlab.el=

* Commands

| Command                             | What it shows                                      |
|-------------------------------------+----------------------------------------------------|
| =gitlab-list-merge-requests=          | Merge request list.  A prefix argument adds =--all=. |
| =gitlab-display-merge-request=        | One merge request in its own buffer.               |
| =gitlab-list-pipelines=               | Pipeline list.  A prefix argument reads flags.     |
| =gitlab-display-pipeline=             | Pipeline fields at the top and jobs below.         |
| =gitlab-display-job-log=              | Live =glab ci trace= output for one job.             |
| =gitlab-export-json=                  | The glab JSON answer of the buffer, in one buffer.  |

The package installs as =gitlab-modes=, the same name as its entry
library:

#+begin_src elisp
(require 'gitlab-modes)

(keymap-set global-map "C-c g m" #'gitlab-list-merge-requests)
(keymap-set global-map "C-c g p" #'gitlab-list-pipelines)
#+end_src

* Detail buffers

A merge request buffer shows every top-level field of
=glab mr view --output json=.  Nested objects become one readable line.
A user becomes =Name (@username)=, a milestone becomes its title and a
pipeline becomes =#ID status= with a link to the pipeline buffer.
=RET= opens the object at point.  =n= loads the notes below the fields.
A field that names one object or one commit, such as =id=, =iid=,
=project_id=, =sha= or =before_sha=, carries the =gitlab-id= face.

A pipeline buffer shows the pipeline fields at the top and the jobs
table below.  =RET= on a job streams its log into a separate buffer.
The log buffer keeps ANSI colors, stays read-only and kills its process
when the buffer dies.  The log has no timeout and streams until =glab=
exits, so a long job keeps writing.  =g= restarts the trace.

The log buffer drops the banner that =glab ci trace= prints before the
trace, because the header line already names the job.  GitLab puts an
ISO 8601 timestamp in front of every line when the job enables runner
timestamps.  A stream identifier follows the timestamp: =00O= for the
runner, =01O= for the standard output, =01E= for the standard error and
=00O+= for the boundary of a section.  The option
=gitlab-job-log-show-timestamps=, on by default, shows the prefix, and
=~= hides or shows the timestamp, the identifier and the space before
the text in the current buffer.  A hidden prefix leaves the text of
the line at column 0 and keeps every space that belongs to the text.

An active region adds a section to the right edge of the mode line.
It shows how many selected trace lines carry a timestamp, and the time
between the first and the last of them.  A line without a timestamp
does not start or end the span, and fewer than two stamped lines show
no section.  The option =gitlab-job-log-show-region-duration=, on by
default, turns the section off.

A project can fetch merge request refs into its remote-tracking
namespace:

#+begin_src gitconfig
[remote "origin"]
    fetch = +refs/merge-requests/*/head:refs/remotes/origin/merge-requests/*
#+end_src

With such a local ref, the merge request buffer lists the commits
between the diff base and the fetched head.  Every commit line shows
the short hash, the subject, the author and the date, and =RET= opens
the commit.  The option =gitlab-merge-request-show-commits=, on by
default, turns the list off, and =gitlab-git-commit-limit= caps it at
50 commits.  A project without the ref shows no commit section.

=d= shows the local changes of the merge request, and =l= shows its
commit log.  Both cover the merge base to the fetched head.  An active
region over commit lines narrows both views to the selected commits,
from the parent of the oldest selected commit to the newest selected
commit.  The commit
view, the changes view and the log view use Magit when Magit is
available.  Magit supplies its whole-tree diff, its commit view and the
=ediff= commands on =E=, so a review can compare a file or a commit
side by side.  The commit log of =l= holds only the commits of the merge
request.  Without Magit the package opens a read-only =diff-mode=
buffer, and =q= closes it.  The package never loads Magit at startup and
never fetches from the network for these views.

The notes request and the jobs request ask for one page of 100 items.
A merge request with more notes, or a pipeline with more jobs, shows
the first page only.

Both detail modes provide these keys:

| Key       | Command                  |
|-----------+--------------------------|
| =RET=       | =gitlab-open-at-point=     |
| =c=         | =gitlab-copy-id=           |
| =w=         | =gitlab-open-web=          |
| =p=         | =gitlab-pop=               |
| =q=         | =quit-window=              |

A merge request buffer also binds =n= for the notes, =d= for the local
changes and =l= for the local commit log.

* List buffers

The list modes derive from =tabulated-list-mode=.  Column sorting,
column resizing and point keeping by row identity come from the parent.
=RET= opens the row, =c= copies its ID and =w= opens its web page.
A header line shows the column names, and the sort column carries the
sort indicator of =tabulated-list-mode=.  A date column carries the
=gitlab-date= face.

=thing-at-point 'url= on a row returns the upstream web URL of that
merge request or pipeline, so =browse-url-at-point= and every caller
that reads a URL work on the table.

* JSON export

=M-x gitlab-export-json= writes the glab JSON answer of the current
buffer into one read-only =js-json-mode= buffer named =*GitLab JSON*=.  A
detail buffer exports one object and a list buffer exports one array.
The command reuses the buffer, so a second export replaces its text.
The buffer is a snapshot: a later refresh of the source buffer does not
change it.  =revert-buffer= in the export buffer reads the source
buffer again.

Both display base modes remap =js-json-mode= to the export command, so
a key or a menu that runs the JSON major mode exports the view instead.
With evil, =y= exports in a detail buffer and in the normal state of a
list buffer.
The export keeps the raw =glab= output of the fetch, so empty arrays and
false values stay as =glab= printed them.  The export adds one trailing
newline when the raw text lacks one.

A pipeline whose answer lacked the jobs array costs one more request,
and the data layer merges two answers.  No single =glab= text describes
that answer, so the export encodes the decoded data again.  A job log
has no JSON answer, and the command signals a user error there.

* Bookmarks

=C-x r m= in a GitLab buffer saves the object and the view.  The
record names the project, the object and the point in the buffer.

A jump restores:

- the project and the directory in which =glab= runs,
- the field line, job row or list row at point,
- the list arguments and the sort column of a list buffer.

A job log restarts its trace, because a trace streams and has no
snapshot.  =bookmark-bmenu= shows the GitLab type in its type column.

A record stores the object as an identifier.  The identifier holds the
project path and a sigil:

| Kind          | Identifier           |
|---------------+----------------------|
| Merge request | =group/project!12=   |
| Pipeline      | =group/project#1001= |
| Job           | =group/project&5001= |

A record without a project keeps the bare ID and reads the project from
=gitlab-repository= or from the directory of the jump.  An Org link and
an xref identifier use the same text, so one syntax names one object
everywhere.

* Automatic refresh

=gitlab-mode.el= sets three buffer-local variables:

- =buffer-stale-function= decides when a refresh is due.
- =revert-buffer-function= starts the asynchronous fetch.  A list
  buffer fetches its collection and a detail buffer its object.
- =auto-revert-mode= calls the stale check at =auto-revert-interval=.

=gitlab-refresh-interval= sets the normal poll interval.
=gitlab-refresh-fast-interval= applies while a status still changes.
=gitlab-refresh-visible-only= stops polling for buffers in no window.
=gitlab-refresh-finished-pipelines= stops polling in a pipeline
buffer whose pipeline and jobs all hold a final status, because
nothing can change there without a user action.  A manual
=M-x revert-buffer= always fetches, so a restarted job appears again.
A list buffer always polls, because a new merge request or pipeline
can arrive at any time.

The fetch is asynchronous.  Unchanged data is not rendered again, so
point and marks survive an automatic refresh that found no change.

* Project selection

A nil =gitlab-repository= lets =glab= infer the project from the
directory of the buffer that ran the command.  Set it to =OWNER/REPO=
or a full namespace path to read another project.  A display buffer
asks =project.el= for the project root of the buffer that opened it,
and uses that root as =default-directory= and as
=gitlab-cli-directory=.  glab therefore runs in the right project, and
project commands in the display buffer see the same project too.

The display buffer also keeps =gitlab-repository= buffer-locally.  A
bookmark jump or an xref definition of another project therefore keeps
that project on every later refresh.

* Optional layers

** Evil

The key bindings install themselves.  If evil is on the load path and
something loads it, =gitlab-modes= loads =gitlab-evil= and enables
=gitlab-evil-mode=.  No extra line is necessary.  To keep the bindings
off, set the option before evil loads:

#+begin_src elisp
(setq gitlab-evil-auto-enable nil)
#+end_src

A user can still turn the bindings on by hand:

#+begin_src elisp
(require 'gitlab-evil)
(gitlab-evil-mode 1)
#+end_src

The mode binds commands in normal state and leaves the evil motions
alone.  A visual selection of list rows followed by =y= copies their
IDs.

Each key that evil already binds goes through a key remap of the evil
command, for example =[remap evil-ret]= for the row open command.  A
remap follows the command and not the key, so a user who moves
=evil-ret= to another key keeps the row open command on the new key.
A key with no evil command, such as =gr=, stays a plain key binding.

** Org links

#+begin_src elisp
(require 'ol-gitlab)
#+end_src

The file registers =gitlab-mr:=, =gitlab-pipeline:= and =gitlab-job:=
link types.  =org-store-link= in a display buffer produces the matching
link.  HTML, markdown and LaTeX export write a web URL when
=gitlab-repository= is set.  Every other backend writes the URL after
the description text.

A path names its project when it holds one, with the sigil of the
bookmark identifier:

#+begin_example
[[gitlab-mr:group/project!12][Fix the dialog]]
[[gitlab-pipeline:group/project#1001][Run]]
[[gitlab-job:group/project&5001][Log]]
#+end_example

A bare ID keeps its meaning and reads the project from
=gitlab-repository= or from the buffer that opens the link.  A point on
a job row of a pipeline buffer stores a =gitlab-job:= link to that job.

** Xref

#+begin_src elisp
(require 'gitlab-xref)
#+end_src

=M-.= opens =mr:12=, =pipeline:1001= or =job:5001=.  In a
display buffer the text properties win, so a job row opens its log
without a typed prefix.

An identifier names its project when it holds one, for example
=mr:group/project!12=.  Completion writes the project form when
=gitlab-repository= is set.

* Nix

#+begin_src sh
nix build          # package; its check phase runs the tests
nix flake check    # package, package-lint, checkdoc, treefmt
nix fmt            # nixfmt via treefmt
nix develop        # emacs with evil, and glab
#+end_src

* Tests

The ERT suite runs offline.  Every request runs =test/mock-glab=, which
reads JSON from =test/fixtures=.  No test opens a network connection.

#+begin_src sh
emacs --batch -L . -L test -L "$EVIL" \
  -l gitlab-test-helpers.el \
  -l gitlab-cli-tests.el \
  -l gitlab-data-tests.el \
  -l gitlab-mode-tests.el \
  -l gitlab-merge-request-tests.el \
  -l gitlab-pipeline-tests.el \
  -l gitlab-export-tests.el \
  -l gitlab-read-tests.el \
  -l gitlab-evil-tests.el \
  -l ol-gitlab-tests.el \
  -l gitlab-xref-tests.el \
  -l gitlab-bookmark-tests.el \
  -f ert-run-tests-batch-and-exit
#+end_src

Set =EVIL= to the directory that holds =evil.el=.  All other tests run
without evil.
